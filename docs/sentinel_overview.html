Why it is built this way

Design decisions

From DESIGN.md. Expand any decision for the reasoning.

Deterministic triage layer before the LLM (yes, added).

An 8B Q4 model on CPU is not reliable at choosing a corrective action (smoke test: it described an exhaust cold spot as "moisture condensation"). Remote monitoring actions must be consistent and auditable. Rules grounded in the process maps decide; the LLM explains. Every conclusion carries a rule ID.

Analytic-specific analyzers for cold_spot, combustion_dynamics, hets_trip; a generic analyzer for anything else.

The three scoped analytics have well-defined physics (TC ring sector, pulsation amplitude/coupling, pre-trip spread build-up). The generic path still runs anomaly scan + all three signature probes, but is always flagged needs_human.

Sensor-vs-process discrimination is explicit in each analyzer.

The most common Tier 2 mistake is a borescope call on a bad thermocouple (or a tuning call on a failed dynamics probe). Each analyzer tests adjacency, step-vs-ramp onset, flatline/saturation and cross-channel coupling before choosing a process cause.

LLM via llama.cpp CLI subprocess (llama-completion.exe, existing binaries), JSON-schema constrained, temp 0, fixed seed.

Already proven on this machine with this GGUF; no python-binding build issues; grammar-constrained JSON makes parsing robust; deterministic. Model reloads per report (~17 s) — acceptable for a one-report-per-case workflow and keeps the process model simple.

LLM writes prose only; site instructions stay deterministic.

Validation showed Granite occasionally garbles step lists ("after the borescope… schedule the borescope") and writes "No concerns" into a free-text concern field. Prose is where the LLM adds value; instructions a technician acts on keep the vetted analyzer wording, and disagreement is a boolean, not parsed text.

Template narrative is a first-class path, not an error path.

Brief requires offline operation without the GGUF. The template uses the same findings, so the structured content (action, evidence, confidence) is identical with or without the LLM.

TS Pulse kept, but only as corroboration/novelty, with robust z-score always computed.

TS Pulse (main = hybrid-allhead, the AD variant) is a 1M-param zero-shot model — fine for "is this window abnormal?", not for root cause. The base used only the last 512 rows per channel, so it missed events in long CSVs; replaced with sliding windows over the full series. If torch/tsfm/weights are missing, z-score is used and the report says so.

ChromaDB + sentence-transformers removed; replaced by structured similarity for cases + BM25 for knowledge text.

Corpus is tiny (a few process maps, tens–hundreds of cases). Structured signature similarity (same analytic, similar depth/width/onset/amplitude…) finds relevant engineer feedback far better than text embeddings, is explainable (score shown), and drops a heavy dependency that has its own telemetry.

Feedback changes outcomes deterministically (not only via prompt).

"Not good + corrected action" on a highly similar case (similarity ≥ 0.80) re-routes the primary action for the new case, with the rule action kept as "alternative" and a review flag. "Good" on similar cases raises confidence. All feedback examples (with reasons) also go into the LLM prompt. Everything is logged in JSONL — the raw material for preference tuning later (python app.py export-prefs).

Human review gate.

Every report is DRAFT — pending Tier 2 review until the engineer marks it. Good → APPROVED; Not good → REJECTED (+ corrected action shown as the engineer's final action). Status is in both report.md and report.json.

Streamlit for the single UI.

Drag-and-drop CSV, markdown rendering and feedback buttons with very little code. Configured local-only: server.address=localhost, browser.gatherUsageStats=false, headless (no telemetry, nothing leaves the machine).

Settings: env vars > settings.local.json (git-ignored) > defaults.

GT_GGUF_PATH points at the existing GGUF (no download, ever). SENTINEL_LLAMA_BIN_DIR, SENTINEL_TSPULSE_DIR likewise point at existing assets.

Thresholds in one place (sentinel/limits.py).

Site limits differ by frame/unit; a Tier 2 engineer must be able to see and change them. Every threshold used is echoed into the audit section.

Decision layer

Triage, confidence and needs_human

Before any LLM runs, a rule-based triage layer turns the analyzer's findings into a decision: severity, cause, one primary action (+ secondary), urgency, escalate, needs_human, review flags and an itemised confidence. Each step records the rule ID that produced it, so the report's audit trail shows exactly why.

Corrective actions (the only actions a report may recommend)
sensor_fix_replaceSensor fix / replace (verify instrument, repair or replace)
borescopeBorescope inspection (combustion / hot gas path hardware)
lvdt_calibrationLVDT calibration (valve / IGV position feedback)
combustion_tuningCombustion tuning (fuel splits / DLN schedule)
control_adjustmentControl adjustment (setpoint, schedule or logic)
monitor_onlyMonitor only (no intervention; trend and re-assess)
escalateEscalate to engineering / OEM combustion SME
Urgency levels
immediateImmediate — act now
before_restartBefore next start / restart
promptPrompt — within days, or at the next shutdown if sooner
next_opportunityNext planned outage / shutdown opportunity
routineRoutine — trend and review at the normal cadence

Cause categories:

  • instrumentation — Instrumentation fault (sensor, wiring, transmitter)
  • combustion_hardware — Combustion hardware / fuel nozzle issue
  • combustion_instability — Combustion instability (dynamics / tuning margin)
  • control_actuator — Control or actuator issue (schedule, LVDT, valve)
  • process_transient — Operational / process transient
  • not_confirmed — Alert not confirmed by the supplied data
  • unknown — Undetermined — needs engineering review

How confidence is built

Confidence starts from the rule support of the winning hypothesis (0.35 + 0.5 × support) and is then adjusted by named factors: margin over the runner-up, data sufficiency (missing channels, short records, weak baseline, poor-quality channels), corroboration by the anomaly scan (TS Pulse +0.05, z-score +0.03), novel anomalies (−0.10), analytic mismatch (−0.10), analyzer review flags (−0.05 each) and engineer feedback on similar cases. An unrecognised analytic is capped at 0.40. High ≥ 0.75 · Medium ≥ 0.50 · Low below.

When the report asks for extra human scrutiny

Every report goes through the review gate. needs_human = true additionally marks it for extra scrutiny when any of these hold:

Can't trust the inputs
  • Unrecognised analytic (generic analysis only)
  • Required channels missing → action escalate
  • Very short record / weak pre-event baseline
Data disagrees
  • Named analytic not confirmed by the data
  • Data matches a different analytic (cross-check)
  • Novel anomaly in a channel the analytic can't explain
  • Two causes too close to call
Process signals
  • Confidence below 0.50
  • Action changed by engineer feedback (confirm it applies)
  • LLM says the facts do not support the action
  • Analyzer flags (e.g. notes give a different first-out)
Output

Report format

report.md (the site report) and report.json (same content, machine-readable) are written for every case. Nine sections:

  1. 1 · SummaryBottom line, action, urgency, severity, confidence, escalate, needs_human, cause
  2. 2 · Recommended corrective actionPrimary + secondary, rationale, site instructions, operating guidance, escalation
  3. 3 · What happenedNarrative + event timeline
  4. 4 · Why — engineering assessmentCause reasoning; alternatives considered and why rejected
  5. 5 · EvidenceEvery finding with its value and the rule / model that produced it
  6. 6 · Confidence and uncertaintyItemised factors, review flags, data gaps
  7. 7 · Similar past casesEngineer-reviewed cases used, and how they changed this report
  8. 8 · Audit trailAnalyzer version, rules fired, thresholds, anomaly engines, LLM model + parameters + output checks, input SHA-256
  9. 9 · Engineer reviewDRAFT / APPROVED / REJECTED, verdict, reason, corrected action, reviewer

4. Why — engineering assessment

The combustion hardware/fuel nozzle issue caused a circumferential imbalance, with hot and cold zones moving together, leading to a gradual spread build-up over 2.3 hours before the HETS protection tripped. Alternatives such as an exhaust thermocouple fault or an operational transient were rejected because a single bad TC cannot produce opposing hot and cold zones, and no load or IGV movement preceded the rise.

Alternatives considered:

  • Exhaust thermocouple / harness fault fooling the spread protection → Sensor fix / replace (rule support 0.10). Not preferred: hot and cold zones moved in opposite directions — a single bad TC cannot do that; gradual multi-hour build-up.
  • Operational transient (load swing / fuel transfer) driving the spread → Control adjustment (rule support 0.10). Not preferred: no load or IGV movement before the rise.

Learning from every review

The feedback flywheel

Every Good / Not good verdict is written to data/feedback.jsonl with the reason and any corrected action. On the next case, Sentinel retrieves reviewed cases of the same analytic and scores them on the analyzer's signature (depth, sector width, onset, amplitude, coupling, trip pattern…), with a small bonus for the same unit.

  • Similarity ≥ 0.80: the engineer-endorsed action replaces the rule action (rule action kept as secondary) and the report is flagged “confirm it applies here”. Approvals of the same action add up to +0.10 confidence; a rejection without correction costs −0.10.
  • Similarity ≥ 0.55: the case is shown in section 7 and given to the LLM as an example, reason included.
  • Other analytics and dissimilar cases are never affected (tested).
  • python app.py export-prefs writes reviewed cases as chosen / rejected preference records — the raw material for preference-tuning the model later.

Limitations and next steps

Limitations
  • Validated on synthetic samples: one clean fault per file, little noise. Real plant data will give lower, more varied confidence.
  • Thresholds in sentinel/limits.py are generic defaults, not frame or site alarm limits.
  • Rule sets exist for three analytics; anything else gets generic analysis and is always flagged for review.
  • TC → combustor-can mapping needs the unit's swirl chart, so reports ask site to apply it rather than naming cans.
  • 1-min historian amplitude cannot resolve the dynamics tone frequency; the high-speed spectrum is still needed.
  • Granite on CPU takes ~3 min per report and can still word things imprecisely (e.g. “immediate” vs urgency “prompt”); the DRAFT gate catches it.
  • No SOE / alarm-list ingestion yet: first-out comes from the notes.
  • Local single-user store; no shared case library across engineers yet.
Next steps
  • Calibrate limits.py to each frame's alarm / trip settings.
  • Pilot on real historian exports from closed cases with known outcomes; measure agreement with the Tier 2 final call.
  • Automatic check that the narrative's urgency words match the decided urgency.
  • Add frame swirl charts so reports can name the cans to borescope.
  • Ingest SOE / alarm lists; add rule sets for exhaust spread advisories and bearing vibration.
  • Keep the model loaded (local llama-server) to remove the per-report load time.
  • Once enough reviews accumulate, use the exported preference data to tune the narrative model.
  • Shared, access-controlled case store so the whole Tier 2 team's feedback compounds.
