Sentinel GT AI · End-to-end AI

From raw historian CSV to corrective action — learned, explainable, and improving as you label

The end-to-end version adds a learned path next to the rule-based Sentinel: a time-series foundation model (IBM TS Pulse, fine-tuned) reads the raw CSV, a similarity index finds the most similar engineer-labeled cases, a novelty check refuses to guess on patterns it has never seen, and a local LLM (Gemma 4 12B) writes the Tier 2 site report. The proven rules run alongside in shadow mode; when the two disagree, the case goes to a human. Everything runs on the engineer's laptop — no cloud, no data leaves the machine.

V2 (residuals, Teach the app, retrain, the single file): docs/sentinel_v2_explainer.html.

For the Tier 2 engineer

  • Drop one CSV or a whole folder. Each case is analyzed in about a second: learned signature and action, rule verdict, agreement, the most similar labeled cases with distances, and a novelty flag.
  • Confirm with one click, or pick the right signature/action from a dropdown — or type a new signature name to create a new class.
  • Your label is used immediately (the next similar case cites it) and the classifier retrains in the background every 5 labels.
  • Ask Gemma for the full site report when you need it — same report format as before, with an audit trail.

For the manager

  • The learned path covers signatures the rules never had analyzers for, and it learns site-specific variants from the engineers' own labels.
  • Shadow mode keeps the rules as a safety net: agreement is measured, disagreements are routed to a person, never auto-released.
  • A learning dashboard shows the model improving as labels come in — accuracy vs rules over time, agreement, novelty and acceptance rates.
  • Runs on the Dell 14 Pro Max (6 GB GPU, partial offload) or CPU-only, installed by one script. Evaluated on synthetic data only so far — see limits.
How it works

Pipeline

CSV + analytic + notes→ Canonical channels→ TS Pulse (fine-tuned)→ Head + similar cases + novelty→ Gemma 4 12B report writer→ Site report + review
same CSV→Rule path (unchanged baseline)→shadow verdict + guardrails → agreement / needs_human
1Canonical channels — any CSV, one fixed viewsentinel/e2e/features.py

Historian exports differ: 16–36 exhaust TCs or 4 zone EGTs, OEM-style tags (TTXD_n, DWATT, CDM_AMP) or plain names, 1-, 5- or 10-minute data, two days or two months. The learned path maps every file to the same 14 channels × 512 points:

  • Rotation-invariant exhaust statistics — coldest and hottest sensor vs the ring median, the coldest pair of adjacent sensors (this is what separates a single bad TC from a cold sector), and a frozen-sensor indicator. A cold sector at TC5 or TC23, on a 16- or 36-TC ring, looks the same.
  • Load-independent residuals for EGT, fuel flow and IGV position (so dispatch changes are not mistaken for faults), dynamics amplitude and probe noise health, vibration, the trip flag, and "everything else" (largest load-independent deviation of CDP, CDT, lube oil, ambient, unknown tags).
  • Robust z-score against the record's own baseline, then signed-log compression: magnitude survives (a 30 °C cold sector is not a 3 °C wobble) while different frames line up.
  • Two views: the whole record (extreme-value pooling, so a 20-minute trip in 60 days still shows) and a 48-hour zoom around the onset of the strongest excursion, at a fixed physical time scale.

No diagnosis rules are involved — only channel-role mapping and generic statistics.

2TS Pulse, fine-tuned on labeled GT casessentinel/e2e/encoder.py · scripts/train_e2e.py

IBM TS Pulse r1 is a ~1 M-parameter time-series foundation model that runs without a GPU. We start from its classification variant (tspulse-block-dualhead-512-p16-r1, from the local models folder) and fine-tune all of it — backbone, mix-channel decoder and classification head — on the synthetic training split: .

The model's semantic register tokens (its summary of the window) become a 672-number embedding per case. The same embedding feeds the classifier head and the similarity index, so "what it predicts" and "what it looks like" are judged in the same space.

3Similarity index and one-shot learningsentinel/e2e/model.py

Every labeled case — synthetic training cases and every case an engineer labels — is stored with its embedding. Each new case retrieves its top-5 neighbours and the report cites them: "similar to case X → action Y, distance d".

One-shot: if the nearest labeled case is within the calibrated match distance () and disagrees with the classifier, the neighbour wins. A single label for a new variant or a new signature therefore works immediately, before any retraining — and is flagged so the engineer confirms it applies.

4Novelty detection — don't force a classcalibrated threshold

If the nearest labeled case is farther than the novelty threshold (, the 98th percentile of nearest-neighbour distances of held-out validation cases), the case is marked novel pattern: no signature is forced, the action is "escalate", and needs_human is set. Labeling it creates the knowledge the next similar case needs.

5Gemma 4 12B writes the report (local, constrained, checked)sentinel/e2e/writer.py · sentinel/llm_runtime.py

The LLM receives the classifier probabilities, the top-5 similar labeled cases (with engineer notes), the novelty result, the largest excursions in physical units, the case notes, and the rule path's shadow verdict. It returns a JSON object constrained by a schema (signature, action, urgency, what happened, why, rationale, concerns), so it can only answer with valid signatures and actions.

  • It may change the classifier's answer only with a reason — and any change is flagged for review. It cannot override "novel".
  • Output checks: valid JSON, the action named in the rationale, every number traced back to the evidence. Site instructions stay vetted text.
  • Runtime: llama-cpp-python, Gemma 4 12B Q4_K_M, device: auto|gpu|cpu, partial GPU offload (~28 of 48 layers on a 6 GB card). A GPU failure is recorded in the audit trail and the report finishes on CPU.
  • No LoRA: a 12B model cannot be LoRA-tuned on this CPU-only laptop or a 6 GB GPU. The model learns in context from the retrieved labeled cases; approved reports are kept as training data for later.
6Rules in shadow mode + guardrailssentinel/e2e/pipeline.py

The original rule-based Sentinel runs on the same CSV. The report shows both answers side by side and whether they agree. needs_human is set when they disagree, when learned confidence is below 0.6, on novelty, on a one-shot match, or when a guardrail fires:

  • GR-TRIP a trip is in the data but the learned signature does not explain one;
  • GR-RULE the rules confirm an event with high confidence but the learned path says normal;
  • GR-DATA / GR-CHAN / GR-FLAT too little data, no exhaust temperatures, flat-lined channels.
Top priority

Drop-in, label on the fly, automatic retrain

  1. Drop one or many CSVs (or type a folder path). A labels.csv in that folder imports real historical labeled cases.
  2. Analyzed immediately — learned signature + action, rule verdict, agreement, top similar case, novelty, needs-human. About a second per file on CPU; the LLM report is on demand.
  3. Label — ✓ Confirm (one click), or choose signature / action from dropdowns, or type a new signature name; optional note. Bulk table for a whole batch: edit the wrong rows, tick, save — or Confirm all unlabeled.
  4. Instant effect — the label and the case embedding go into the similarity index at once; the very next similar case cites it.
  5. Background retrain after every N labels (default 5, configurable) or on Retrain now. A head retrain takes seconds on CPU.
  6. Versioned — every retrain is a new version (v0001, v0002 …) with its held-out score; activate any version or roll back in one click.

What is stored (all local, data/e2e)

  • labels.jsonl — every label (signature, action, Good/Not good, note, reviewer), append-only.
  • emb/ — the TS Pulse embedding of each analyzed case.
  • registry/ — retrained heads with metadata; current.json = active version.
  • metrics.jsonl — analysis, label and retrain events that drive the dashboard.
  • taxonomy.json — signatures engineers created, with their actions.

Export everything as a training set (labels.csv + CSVs) with app.py e2e export-dataset; re-fine-tune TS Pulse with scripts/train_e2e.py --extra. Real historical Tier 2 cases drop in the same way.

How to run

Install (any Windows PC)

python sentinel_gt_ai.py setup
# offline models from a USB copy:
python sentinel_gt_ai.py setup --models-from E:\models
python sentinel_gt_ai.py doctor

CUDA build of llama-cpp-python when an NVIDIA GPU is present, CPU build otherwise (automatic fallback). Models SHA-256 verified. See DEPLOY.md.

Use

python sentinel_gt_ai.py                  # UI, http://localhost:8501
python sentinel_gt_ai.py --device cpu     # force CPU
python sentinel_gt_ai.py e2e run --folder D:\exports --analytic "Exhaust Cold Spot"
python sentinel_gt_ai.py e2e label --case SGT-... --signature tc_sensor_fault
python sentinel_gt_ai.py train --quick --device auto
python sentinel_gt_ai.py e2e versions | rollback | retrain
python scripts\eval_e2e.py      # re-run this evaluation

Be careful

Limitations and next steps

Limitations

  • Synthetic only. Training and evaluation data come from one generator. Real historian data has failure modes, mixed faults and operating modes it does not.
  • The novelty threshold was calibrated on synthetic validation cases — expect more novelty flags on real data at first; each label reduces them.
  • The classifier does not read the notes; only the LLM does (and any change it makes is flagged).
  • On this CPU-only laptop a Gemma report takes minutes; the drop-in analysis never waits for it.
  • No LoRA fine-tuning of the LLM (hardware); in-context learning from retrieved cases instead.
  • Decision support only — DRAFT until a Tier 2 engineer reviews it; rules stay as guardrails.

Next steps

  1. Run in shadow on real Tier 2 cases for a few weeks; label everything through the drop-in page.
  2. Export the labels, re-fine-tune TS Pulse with --extra, re-run eval_e2e.py on a real held-out set.
  3. Re-calibrate the novelty threshold on real validation cases.
  4. Use the exported approved reports for a LoRA of a small model once a suitable GPU is available.
  5. Only then consider letting agreed, high-confidence cases skip the second look.
